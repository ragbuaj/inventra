# Rencana Implementasi: PWA untuk aplikasi web Inventra

- Tanggal: 2026-08-27
- Spec: `docs/superpowers/specs/2026-08-27-web-pwa-design.md` (40 acceptance criteria, tanpa pertanyaan terbuka)
- Branch: `feat/web-pwa`
- Fase: Plan (`/plan`). Belum ada kode yang ditulis saat dokumen ini dibuat.

## Ikhtisar

Menjadikan aplikasi web Inventra sebuah PWA berkedalaman "installable dan andal": bisa
dipasang ke layar utama Android dan iOS, aset build beserta shell ter-precache, jaringan
putus memberi shell aplikasi alih-alih halaman error browser, dan deploy baru sampai ke
pengguna lewat ajakan yang mereka kendalikan. **Tidak ada satu pun respons API yang
di-cache.** Web Push, antrean tulis offline, dan perubahan backend berada di luar cakupan.

Pekerjaan ini seluruhnya di `frontend/` plus dokumen. Backend, migrasi, OpenAPI, dan
aplikasi Flutter tidak disentuh sama sekali.

## Keputusan arsitektur

Sebelas keputusan sudah dikunci di spec. Empat di antaranya yang paling menentukan bentuk
tugas di bawah:

1. **Shell dipaksa jadi berkas statis lewat prerender rute `/`.** `nuxt build` hari ini
   tidak menghasilkan satu pun HTML di `.output/public/` — shell dirender Nitro saat
   runtime, sehingga tidak ada yang bisa di-precache. Karena `ssr: false`, HTML hasil
   prerender hanyalah kerangka kosong tanpa data pengguna.
2. **`registerType: 'prompt'`, bukan `autoUpdate`.** Muat ulang otomatis bisa membuang
   isian formulir aset yang sedang diketik.
3. **Tidak ada runtime caching apa pun.** Konsekuensi kerasnya: `Cache Storage` wajib nol
   entri ber-URL mengandung `/api/`. Ini dibuktikan lewat pembacaan `caches` di e2e, bukan
   diperiksa mata — sebab di produksi API se-origin dengan frontend, sementara di dev beda
   origin, jadi kesalahan semacam ini tidak akan pernah terlihat saat dev.
4. **Ikon diturunkan dari mark aplikasi yang sudah ada**, bukan dari logo korporat BTN dan
   bukan karya visual baru.

**HASIL GERBANG (2026-08-27): LULUS, dengan dua penghalang yang harus dibongkar dulu.**
Keduanya ternyata bukan soal dukungan Nuxt 4, dan yang pertama membuat jalur cadangan yang

2. Seluruh 86 berkas tes runtime Nuxt mati saat boot: plugin klien modul mengimpor virtual

   sebagai nama berkas. Diperbaiki lewat sakelar resmi modul,
   `pwa.client.registerPlugin: false`, khusus di lingkungan tes.

Sesudahnya: `pnpm build` menerbitkan `sw.js` dan `manifest.webmanifest`, dan `pnpm dev`

**HASIL (2026-08-27): SELESAI, dengan satu perubahan lingkup yang disetujui pemilik produk.**

Yang dibangun: `frontend/pwa/workbox.ts` sebagai satu-satunya sumber strategi caching
(dikunci `test/unit/pwa-workbox.spec.ts`, 11 tes), plus `nitro.prerender.routes: ['/']` dan
`pwa.workbox` di `nuxt.config.ts`. Angka hasil build: 196 entri precache, **nol** ber-URL
`/api/`, shell terbit sebagai entri `url:"/"`, `createHandlerBoundToURL("/")` terpasang,
`registerRoute` hanya satu (rute navigasi) sehingga tidak ada satu pun aturan runtime caching,
`cleanupOutdatedCaches()` aktif, denylist `[/^\/api\//,/^\/health(?:[/?]|$)/]`. Shell hasil
prerender berisi `<div id="__nuxt"></div>` kosong dan `__NUXT_DATA__` hanya memuat
`prerenderedAt` serta `serverRendered:false` — tidak ada data pengguha.

Ketiga tes baru dibuktikan bisa merah lewat mutasi terarah: menghapus entri denylist `/api/`,
menambahkan satu aturan runtime caching untuk `/api/`, dan menghapus `navigateFallback` —
masing-masing menjatuhkan tepat tes yang dimaksud, lalu hijau lagi setelah dikembalikan.

Pembuktian runtime dilakukan di Chromium sungguhan (bukan panel browser dalam aplikasi, yang
menolak mendaftarkan service worker sama sekali dengan "An unknown error occurred when
fetching the script" walau `/sw.js` dan `/workbox-*.js` terlayani 200): service worker
mencapai `activated` pada scope `/`, 195 entri di Cache Storage dengan nol `/api/`, luring di
`/aset` dan `/en/` tetap merender shell, `fetch('/api/v1/assets')` saat luring ditolak
jaringan alih-alih dijawab cache, dan daring kembali normal. Di `pnpm dev`, `/sw.js` jatuh ke
SPA fallback Nitro (HTML) sehingga tidak ada service worker yang terdaftar.

**Perubahan lingkup: `NUXT_PUBLIC_API_BASE` menjadi nilai build-time.** Prerender rute `/`
membekukan `runtimeConfig.public.apiBase` ke dalam HTML statis. Dibuktikan langsung: dengan
`NUXT_PUBLIC_API_BASE=https://example.test/api/v1` saat container jalan, `GET /` tetap
mengembalikan `apiBase:"http://localhost:8080/api/v1"` sementara `GET /aset` mengembalikan
nilai runtime-nya. Ini merusak produksi — CD membangun `ghcr.io/ragbuaj/inventra-frontend`
tanpa build args dan `docker-compose.prod.yml` menyuntikkan `https://${DOMAIN}/api/v1` saat
container jalan, sehingga halaman depan produksi akan menunjuk ke `localhost:8080`, dan
service worker akan mem-precache shell rusak itu untuk seluruh navigasi. CI e2e dan kedua
compose dev tidak terdampak karena nilainya sudah sama dengan default.

Sifatnya melekat pada arsitektur precache-shell: begitu service worker menjawab navigasi dari
berkas yang sudah di-precache, penyuntikan env saat runtime tidak lagi bisa menjangkau
HTML-nya. Pemilik produk memilih **membekukan nilainya saat build** (2026-08-27), pendekatan
standar industri untuk SPA/PWA. Karena itu tugas ini menyentuh berkas ops yang semula
dinyatakan di luar cakupan: `frontend/Dockerfile` (`ARG NUXT_PUBLIC_API_BASE` sebelum
`pnpm build`), `.github/workflows/deploy.yml` (`build-args`, domain dari variabel repo
`PROD_DOMAIN` dengan fallback domain produksi yang berlaku), `docker-compose.prod.yml` dan
`docker-compose.yml` (env runtime dipindah ke `build.args` supaya tidak ada dua sumber
kebenaran), serta `docs/DEPLOYMENT.md`. Konsekuensi yang harus diingat: image GHCR kini
terikat pada satu domain, jadi lingkungan lain butuh build sendiri.

**Catatan terpisah, bukan bagian tugas ini:** `pnpm test` keluar dengan kode 1 walau 130
berkas dan 1872 tes lulus, karena satu `EnvironmentTeardownError` (impor malas
`app/pages/assets/[tag]/edit.vue` ke `useConfirm.ts` selesai setelah lingkungan tes
dibongkar). Sudah dipastikan **pre-existing**: menjalankan suite penuh dengan `nuxt.config.ts`
dikembalikan ke isi HEAD menghasilkan error yang identik. Berkasnya lulus bersih bila
dijalankan sendirian tiga kali berturut-turut, jadi penyebabnya kontensi suite penuh.

### Tugas 5: e2e service worker, offline, dan keamanan cache

**Deskripsi:** Spec e2e tersendiri yang membuktikan perilaku yang tidak bisa dibuktikan tes
unit: service worker benar-benar aktif, offline benar-benar memberi shell, dan yang
terpenting **Cache Storage benar-benar bersih dari `/api/`** setelah dipakai login dan
membuka layar berdata. Ini tes keamanan, bukan tes kenyamanan.

**Acceptance criteria:**
- [x] Manifest terlayani 200, JSON-nya terurai, bidang wajibnya benar; setiap URL ikon menjawab 200 dengan tipe gambar.
- [x] Service worker mencapai `activated` dalam batas waktu wajar.
- [x] Setelah login dan membuka layar berdata, pembacaan `caches` lewat `page.evaluate`
      memberi **nol** entri ber-URL mengandung `/api/` — diperiksa sebelum dan sesudah logout.
- [x] Offline setelah satu kunjungan daring: navigasi menampilkan shell aplikasi, bukan halaman error browser.
- [x] Offline: layar berdata menampilkan keadaan error aplikasi, bukan data basi.
- [x] Rute `/en/` bekerja offline dengan shell yang sama.
- [x] Muat ulang daring setelah offline mengembalikan keadaan normal.

**Verifikasi:**
- [x] `pnpm exec playwright test e2e/pwa.spec.ts --workers=1` hijau, dijalankan tiga kali berturut-turut untuk menyaring kerapuhan.
- [x] Tiap tes dibuktikan bisa merah lewat mutasi terarah — minimal: hapus satu entri
      denylist, dan tambahkan satu aturan runtime caching untuk `/api/`; keduanya harus
      membuat tes keamanan cache gagal. Kembalikan setelahnya.
- [x] Data uji dibersihkan sendiri di `afterAll` bila tes sempat membuat data.

**Ketergantungan:** Tugas 4.

**Berkas yang kemungkinan disentuh:**
- `frontend/e2e/pwa.spec.ts`
- `frontend/e2e/helpers.ts` (hanya bila butuh helper baru)

**Perkiraan cakupan:** M

**Menutup acceptance criteria spec:** 15, 17, 18, 20, 21, 22, plus pembuktian 12 dan 16.

**HASIL (2026-08-27): SELESAI. 11 tes di `frontend/e2e/pwa.spec.ts`, hijau tiga kali berturut-turut.**

Satu tes **di luar daftar acceptance criteria** ditambahkan, dan tanpa ia mutasi yang
diminta rencana ini tidak akan berarti: "lets a denylisted request fail offline rather than
answering it with the shell". Sebabnya ditemukan saat menulis mutasi — `navigateFallbackDenylist`
hanya berlaku pada **navigasi**, bukan pada caching, jadi menghapus entri `/api/` tidak
menyentuh satu pun tes keamanan cache seperti yang diperkirakan rencana. Lebih jauh, saat
daring perilakunya tidak bisa dibedakan sama sekali: SPA fallback Nitro mengembalikan shell
yang sama untuk path tak dikenal. Luring memisahkan keduanya — navigasi yang masuk denylist
kehilangan fallback dan gagal apa adanya, sementara rute aplikasi tetap mendapat shell. Tes
itu memakai rute aplikasi nyata sebagai kontrol di context luring yang sama, supaya asersinya
tidak bisa lulus hanya karena luring membuat semuanya gagal.

**Mutasi yang dijalankan, masing-masing dengan build ulang (service worker dibangun saat build):**

1. Hapus `/^\/api\//` dari denylist. Merah tepat di tes denylist tadi (10 lulus, 1 gagal).
2. Tambah `runtimeCaching` NetworkFirst untuk `/api/`. Merah tepat di tes keamanan cache —
   **16 URL API mendarat di Cache Storage**, yang persis merupakan risiko produksi yang dijaga
   tes ini. Catatan yang perlu diingat: tes "keadaan error di layar berdata" **tetap lulus**
   di bawah mutasi ini (NetworkFirst tanpa entri untuk kueri pencarian itu tetap jatuh ke
   error), jadi tes keamanan cache-lah satu-satunya yang menangkapnya.

Keduanya dikembalikan sesudahnya dan suite kembali 11 dari 11.

**Perubahan kecil di kode aplikasi:** `app/components/UserMenu.vue` mendapat
`data-testid="user-menu-trigger"` dan `data-testid="user-menu-logout"`. Belum ada satu pun
spec e2e yang pernah keluar lewat UI, dan pemicu menu pengguna tidak punya nama yang bisa
dijangkau (isinya inisial nama, yang berubah mengikuti data seed). Perubahannya murni
penambahan atribut — tidak ada perilaku maupun tata letak yang berubah.

**Tidak ada data uji yang dibuat**, jadi tidak ada yang perlu dibersihkan.

**Catatan lingkungan lokal:** port 8080 sempat dipegang container `palang-api` dari proyek
lain (`restart: unless-stopped`, ikut hidup saat Docker Desktop dibuka). Dihentikan atas
persetujuan pemilik produk; ia tidak akan hidup sendiri lagi sampai `docker start palang-api`.

   assertion yang sama. Service worker yang mengganggu akan memberi kegagalan yang berpindah.
